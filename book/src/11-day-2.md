# Day-2 operations

## Changing a setting

Edit the overlay, commit, push, and **Sync**. For settings BNK can change in
place (the licence hand-off, TMM replicas, tuning values) `bnk up` runs
`terraform plan` against the applied state and applies only the difference.
The **BNK version is not one of them** — see the next section. Settings
roksbnkctl treats as *create-time* — the BNK line (2.3 ↔ 2.4), the FLO
namespaces, the cluster network mode — are refused on an applied workspace:
tear down first, then change them.

## Upgrading BNK — there is no in-place upgrade

**BNK 2.3 and 2.4 do not support in-place upgrades.** The only supported path
is `bnk down` (uninstall the old version) followed by `bnk up` (install the
new one). The Application enforces that: when `config.bnk.manifest_version`
in the overlay differs from the version recorded by the last apply
(`terraform.applied.tfvars` on the PVC) and BNK is installed, the `bnk-up`
hook **never** runs `bnk up` against the old install. What it does instead is
chosen by `upgrade.strategy`:

| `upgrade.strategy` | Behaviour on a version change |
|---|---|
| `down-then-up` (default) | The preflight gate announces the change; the `bnk-up` hook runs `bnk down --auto`, then `bnk up --auto`, in the same sync. The status reads *upgrading BNK 2.4.0-EA → 2.4.1: bnk down (no in-place upgrade), then bnk up* while it runs. |
| `refuse` | The preflight gate fails the sync with instructions: set `lifecycle: down`, sync, change the version, set `lifecycle: up`, sync. For teams that want the two steps as two separate, separately approved syncs. |

So an upgrade is: bump `config.bnk.manifest_version` in the overlay (and the
`roksbnkctl.io/bnk-version` label on the Application), commit, **Sync** — and
expect the data plane to be down for the length of a destroy plus an install.
A line change (2.3 → 2.4) follows the same path; roksbnkctl itself refuses a
line change on an applied workspace, which is why the down happens first.

The `bnk-up` log makes the sequence explicit:

```text
[status] running deployed=unknown — bnk up in progress
== BNK version change 2.4.0-0.0.1 -> 2.4.1-0.0.1: running bnk down first (BNK does not support in-place upgrades)
… terraform destroy …
== bnk down complete; installing 2.4.1-0.0.1
… terraform apply …
[status] succeeded deployed=true — bnk up completed
```

A re-sync with an unchanged version is still a no-op plan, as before.

## Upgrading the runner

Bump `runner.tag`. Every roksbnkctl release ships a matching runner image with
its embedded Terraform, so the CLI and the HCL never skew. Read the roksbnkctl
changelog for migration notes before crossing a major version.

## Re-syncing

Safe at any time (Step 5). A no-op sync takes a few minutes: the gates plus a
`terraform plan` that finds nothing to do. To avoid the churn on every Git
change, keep the Application on manual sync — which is also what makes
**Sync** the approval step.

## Sync windows and who may sync

The `bnk` AppProject defines a `bnk-operator` role that may `get`, `sync` and
read `logs` but not edit the Application. Bind your operators' group to it
(`groups:` in the project, or Argo CD RBAC), and consider a `syncWindows` block
to allow syncs only in a maintenance window — the project file has one
commented out.

## A stuck apply

Every hook has `activeDeadlineSeconds` (`timeouts.*`): `bnk-up` defaults to
two hours. When the deadline passes the Job fails, the trap writes
`outcome: failed`, and the Application turns Degraded. Terminating the Argo CD
*operation* does **not** kill the Job — Kubernetes keeps running it, and the
Terraform state lock is held until it exits. If you must stop it early:

```bash
kubectl -n bnk-sm-cli delete job bnk-up            # then, if the lock is stuck:
kubectl -n bnk-sm-cli create job --from=job/bnk-init unlock-shell   # any runner pod with the PVC …
# … and inside it: terraform -chdir=/work/.roksbnkctl/sm-cli/state/tf-source/embedded-terraform force-unlock <id>
```

then **Sync** again.

## One run per workspace

The PVC is `ReadWriteOnce` and Terraform locks its state, so two syncs of the
same Application cannot run concurrently — Argo CD serialises operations per
Application anyway. Different workspaces are independent.

## Rotating the API key

Update the `bnk-secrets` Secret (or the External Secrets source). The next
hook pod picks it up; nothing is cached on the PVC except the `config.yaml`
that `bnk-init` rewrites on every run.

## Moving the state off the PVC

roksbnkctl supports a COS (S3-compatible) remote-state backend with native
locking; it is configured in the same `config.yaml`:

```yaml
config:
  state:
    backend: s3
    s3:
      endpoint: https://s3.us-south.cloud-object-storage.appdomain.cloud
      bucket: bnk-tfstate
      region: us-south
      key_prefix: argocd
```

The COS HMAC key pair goes into `bnk-secrets` (see the values reference).
With remote state the PVC holds only the workspace's hand-off files, so losing
the hub does not lose the Terraform state.
